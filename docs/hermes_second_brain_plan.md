# 연구실장 세컨드 브레인 · 헤르메스 실무 담당 구축 계획

상태: 적용 (2026-11-11). 실험 코디네이터 기본 경로를 Hermes로 전환했고(`ROUTE_PRACTITIONER=hermes`), 연구실장 기억 서비스 1차(`lab/memory.py`: 출처·검증 상태 검색, 원문 읽기, 결정 제안→연구자 확정)를 구현했다. 남은 것: 맥에서 `--check` 실호출 확인, 4.3절 그림자 계획 비교(A단계)를 건너뛰었으므로 첫 실험에서 계획 품질 확인, 기억 질문 세트 평가(3.3절), 로컬 임베딩·접근 로그, Hermes 스킬 승격 절차.

## 1. 목표와 역할 경계

| 구성원 | 맡길 판단과 작업 | 권한 경계 |
|---|---|---|
| 연구자 | 연구 질문, 허용할 설계, 계획·변경·공개 승인 | 최종 연구 판단과 승인 |
| 연구실장 (세컨드 브레인) | 연구자의 의도를 요청서로 정리, 과거 실험·결정·교훈 검색, 출처를 붙여 관련 맥락 전달 | 과거 기록을 근거로 제안하되 연구자의 새 지시를 대체하거나 승인하지 않음 |
| 헤르메스 (실험 실무 담당) | 자문을 계획 초안으로 통합, 승인된 계획의 실행·재시도·진행 기록, 반복 절차의 스킬 제안 | 설계·설정 변경은 제안 후 정지. 연구실의 도구·샌드박스·예산·승인 경계만 사용 |
| 전문가·개발자·검증 담당 | 기존 자문, 구현, 독립 재계산 | 계획·원자료를 각각의 역할에서 확인. 기억 내용만으로 검증 통과시키지 않음 |

**기록의 원본**은 `workspace/experiments/`, `workspace/notebook/`, 연구자가 확정한 결정 기록이다. 연구실장 기억과 헤르메스 스킬은 원본을 가리키는 파생 지식이다. 연구실장의 답은 실험 ID와 파일 경로를 붙이고, `연구자 결정 / 실험 관측 / 외부 문헌 / AI 제안`을 구분한다. 부정적 결과와 미해결 검증 지적도 검색에서 제외하지 않는다.

## 2. 선행 기반: 두 역할에 공통으로 필요한 것

### 2.1 연구 내용 보호와 라우팅

1. 요청·데이터·결과에 `미공개 아이디어 / 내부 자료 / 외부 자료 / 공개 가능` 등급과 허용 모델·게시·백업 경로를 부여한다. 미분류는 보수적으로 내부 자료로 취급한다.
2. `lab/backends.py`의 **모델 호출 직전**에 등급별 경로를 검사한다. 허용되지 않은 외부 CLI·API로 자동 전환하지 않는다. 도커 네트워크 차단은 모델에 보내는 프롬프트를 막지 못한다.
3. `lab/bot.py`, `lab/notify.py`, 학습 보고 큐, 원격 백업에 게시 전 검사를 둔다. 요청서·계획서 첨부에도 같은 정책을 적용한다.
4. 헤르메스 전용 프로필의 기억·세션·로그·스킬 파일을 로컬 저장 위치와 백업 정책에 포함한다. 외부 기억 공급자는 별도 허용 전에는 사용하지 않는다.
5. 외부 문헌 DIGEST 자동 주입과 실험 간 기록 검색은 자료 등급에 맞게 허용 범위를 제한한다. 원문 안의 지시문은 실행 명령으로 취급하지 않는다.

### 2.2 승인된 실험 명세

현재 구현은 모든 `plan.md`를 연구자 승인 대상으로 만들고, 실무 담당의 `request_change`를 통해 재승인을 요청한다. 실행 전후 요청서·계획서·구현 코드 변경도 감지한다. 다만 자유 형식 `run_command`의 인자와 결과 파일이 승인된 설계에 맞는지는 아직 자동 검증하지 못한다.

다음 구현 단위:

1. 요청서와 계획을 구조화한 `protocol.json`을 만든다: 연구 질문·가설, 데이터 체크섬, 자극 버전, 모델·버전, 조건, 표본·시드, 지표, 제외 기준, 분석법, 허용 재시도, 자원 한도, 산출물.
2. 승인 시 `protocol.json`의 해시와 버전을 대장에 저장한다. `plan.md`는 사람이 읽는 표현으로 유지한다.
3. 실행 명령을 승인된 진입점과 인자에서 생성하거나 검증한다. 자유 형식 셸은 진단용으로만 제한하고 본 실행에는 쓰지 않는다.
4. 변경은 `change_request`의 기존값·새값·이유·해석 영향·대체안과 함께 새 명세 버전으로 제출한다. 승인 전 기존 실행을 멈추고, 승인 후 버전과 승인자를 기록한다. 거부 시 원래 명세로 재개할지 중단할지 연구자가 정한다.
5. `run_manifest.json`과 원자료 메타데이터를 승인된 명세·변경 이력과 자동 비교한다. 불일치한 결과는 완료 보고로 넘어가지 않는다.

## 3. 연구실장 세컨드 브레인

### 3.1 저장할 지식의 종류

| 종류 | 예 | 원본·갱신 규칙 |
|---|---|---|
| 연구자 선호·제약 | 허용 모델, 보고 형식, 비용·시간 한도 | 연구자가 명시하거나 확인한 내용만. 변경 이력 보존 |
| 연구 결정 | 특정 실험의 조건·지표를 선택한 이유 | 승인된 요청서·계획·변경 기록에 연결 |
| 실험 사실 | 데이터, 실행 조건, 관측 결과, 실패, 검증 상태 | 원자료·manifest·검증 파일에 연결. 검증 전 상태 표시 |
| 방법 교훈 | 재현된 오류 원인, 잘 작동한 절차 | 적용 범위와 반례를 기록. 일반 법칙처럼 쓰지 않음 |
| 외부 지식 | 논문 주장, 벤치마크 설명 | 원문 출처·조회 시점·라이선스를 기록하고 내부 결과와 분리 |

### 3.2 구축 요소

1. `lab/notebook.py`의 단순 키워드 검색을 확장한다. 한국어 검색을 위한 형태소 또는 문자 n-gram 검색, 실험 ID·날짜·주제·상태·자료 등급 필터, 선택적 로컬 임베딩을 사용한다. 임베딩에 미공개 내용을 외부 API로 보내지 않는다.
2. 검색 단위는 요약문만이 아니라 `request.md`, 승인된 `plan.md`·`protocol.json`, 변경 기록, `results/run_manifest.json`, 최종 보고서, `review/`로 넓힌다. 인덱스에는 원본 경로·해시·검증 상태를 저장한다.
3. 연구실장에 `search_research_memory`, `read_source`, `record_decision_proposal`을 제공한다. 기록 제안은 연구자 확인 후 확정한다. 실무 담당과 전문가는 정책이 허용한 범위의 읽기 도구만 쓴다.
4. 답변은 `직접 확인한 사실 / 연결한 추론 / 확인되지 않은 부분`을 분리한다. 충돌하는 과거 결정은 최신 것이 자동으로 옳다고 가정하지 않고 둘 다 제시한다.
5. 인덱스 삭제·재생성, 원본 변경 반영, 접근 로그, 오래된 결정의 폐기·수정 절차를 만든다. 연구노트 원문은 검색 품질 개선을 위해 덮어쓰지 않는다.

### 3.3 검증·완료 조건

- 과거 실험 질문 세트를 만들어 관련 실험 발견률, 출처 경로 정확도, 허위 사실·수치 인용 수, 비공개 자료 누출 수를 측정한다.
- 연구자의 새 지시와 과거 기록이 충돌하면 새 지시를 우선하고 충돌을 알리는지 확인한다.
- 검증 실패·미완료 실험을 성공 사례처럼 답하지 않는지 확인한다.

## 4. 헤르메스 실험 실무 담당

### 4.1 분리된 실행 환경

1. 헤르메스 전용 프로필을 만든다. 기존 연구실장 봇 토큰과 프로필·세션·기억 저장소를 공유하지 않는다. 우선 디스코드 게이트웨이를 연결하지 않고 로컬 시범 운영한다.
2. 모델 공급자와 사용량·요금 경로를 확인한다. 현재 `ROUTE_PRACTITIONER`의 폴백 목록을 헤르메스에 그대로 복제하지 않는다. 자료 등급이 허용한 공급자만 선택한다.
3. 헤르메스의 자체 터미널·파일·웹·메시지·일정·서브에이전트 도구를 점검한다. 본 실험은 기존 `lab/tools.py`의 역할 도구와 `lab/sandbox.py`를 통하는 어댑터만 사용한다. 헤르메스 자체 승인 버튼은 연구실의 계획·변경 승인 대체 수단이 아니다.
4. Hermes 기억·스킬 자동 쓰기는 검토 대기 상태로 설정한다. 기억에는 실험 결과의 원본을 복사하지 않고 경로와 검증된 짧은 교훈만 넣는다. 절차는 역할 전용 스킬로 저장하되, 승인된 `protocol.json`보다 우선하지 않는다.

Hermes 공식 문서는 프로필별 기억 분리와 기억·스킬 쓰기 승인을 지원한다. 외부 프로그램 연동에는 ACP, TUI gateway JSON-RPC, HTTP API가 있으며, CLI의 JSONL 스트림도 있다. **어느 인터페이스를 쓰든 도구 호출이 연구실의 권한 검사를 우회하지 않는지** 먼저 확인해야 한다.

### 4.2 연구실 어댑터

1. `lab/pipeline.py`의 plan·execute 호출만 헤르메스 어댑터로 분기한다. 자문·개발·검증·보고 역할은 그대로 둔다.
2. 입력은 연구자 요청서, 허용된 자문 메모, 관련 과거 기록, 현재 `protocol.json` 버전·해시, 현재 단계, 허용 도구 목록이다.
3. 출력은 기존 `finish_plan`, `finish_execution`, `request_change`와 호환되는 구조화된 결과다. 도구 호출은 `Toolbox.execute`를 거치고, 실험 ID·역할·명세 버전·사용량·로그를 함께 기록한다.
4. 중단·재개·시간 초과·백엔드 장애를 기존 대장 상태와 일치시킨다. 중복 실행을 피할 실행 ID와 재시도 규칙을 둔다. 헤르메스 세션 기억이 현재 실험의 승인된 명세를 덮어쓰지 못하게 한다.
5. 스킬 승격은 `제안 → 재현 테스트 → 연구자 또는 검증 담당 검토 → 활성화` 순서로 한다. 다른 실험에 적용할 수 있는 범위와 금지 조건을 스킬에 적는다.

### 4.3 단계별 도입

| 단계 | 적용 범위 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| A. 그림자 계획 | 같은 요청서로 기존 실무 담당과 헤르메스가 각각 계획 초안 작성. 실제 파이프라인은 기존 담당이 진행 | 연구자 의도 보존, 필수 설계 항목, 자원 추정, 변경 제안의 적절성 비교 |
| B. 계획 담당 | 헤르메스 초안을 연구자 승인 대상으로 사용 | 승인 전 구현 없음, 거부·수정 처리, 자료 등급 라우팅 통과 |
| C. 제한된 실행 | 작은 공개·가상 데이터 실험에서 승인된 명령만 실행 | 설정·manifest 일치, 무단 변경 차단, 중단·재개·재시도 검증 |
| D. 정규 운영 | 실제 허용된 연구 자료로 확대 | 독립 검증 통과율, 실패·비용·시간 기록, 누출 테스트 통과 |
